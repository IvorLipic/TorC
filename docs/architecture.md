# Architecture

## Goal
A static website (GitHub Pages, served under `/TorC/`) of interactive lessons on TorC. Every number a learner sees must be
traceable to a real run of the library; learners can edit inputs and see results recompute.

## Pipeline
```
TorC @ pinned ref ──► tools/trace/*.cpp (real run) ──► site/data/*.json ──┬─► site/js/ops/*.js   (op registry: forward/backward + paper-work text)
                                                                         ├─► site/js/engine.js  (graph + backward pass, tested == JSON)
                                                                         ├─► site/js/explain.js (rule + numbers as KaTeX "paper work")
                                                                         └─► site/js/lessons/*.js + widgets/ (lesson text and interactive parts)
```
- **Trace programs** (`tools/trace/`) build against TorC fetched by CMake `FetchContent` at the ref in `tools/trace/TORC_REF`
  (a release tag, or the commit SHA the tag points to). `run.sh --check` regenerates and fails on drift.
- **Trace JSON** (`site/data/*.json`): an object `{schema:"torc-trace/1", library, generator, kind, lesson, scenes[], …extra tables}`.
  `scenes[] = {id,title,expression,note,root,root_has_grad,nodes[],finite_difference}`;
  `nodes[] = {name,op,role("leaf"|"op"),requires_grad,inputs[],value{shape,values},grad{shape,values}|null}`. `inputs` are read
  from the real `TapeEntry`; `finite_difference` holds numerical vs. analytic gradients. The site loader reads `scenes[]` at the
  top level and ignores every other key (they stay reachable from lesson text through `T('files.<file>.<key>…')`).
- **Op registry** (`site/js/ops/`): one module per op (add, sub, mul, relu, sum, mean, matmul, transpose, mse) holding everything
  about it: `forward`, `backward` (raw gradients; reduction to the input shape is centralised in `runBackward`), the general rule
  as LaTeX (`texForward`, `texBackward`), the one-sentence reasons (`whyForward`, `whyBackward`) and the rule with real numbers
  substituted (`forwardNumbers`, `backwardNumbers`). `engine.js` and `explain.js` are generic consumers; the op-card page planned in
  the content plan will be generated from the same table. A test requires every registered op to appear in some trace scene.
- **Engine** (`engine.js`): `buildGraph`, `runBackward`, `timeline` over a scene, using the registry. It exists only so learners
  can edit inputs; the tests assert it reproduces every value and gradient of every real run, agrees with finite differences,
  and that every generated LaTeX string parses in KaTeX.
- **Explain** (`explain.js`): assembles the math windows (rule, numbers, accumulation `c1 + c2 + c3`, broadcast-reduction
  bookkeeping) from the registry's text.

## Site layout
```
site/
  index.html                  course map (shell; js/home.js renders it from course.json)
  course.json                 hand-written: parts {id,title,kind?:"lab"} → lessons {id,title,outcome,prereqs,symbols,trace,est_minutes,
                              status: published|draft|planned, widgets, code}
  lessons/<id>/index.html     committed ~15-line shell: loads ../../js/lesson-boot.js (generated by check_site --write-shells)
  anchors.json                hand-written: course-wide anchors {name: trace path} (tools/anchors.mjs → data/anchors.json)
  glossary.json               hand-written: {schema:"torc-glossary/1", terms:{key:{term, forms, short, lesson}}} (term popovers)
  css/    base.css (tokens, lesson furniture, v3 blocks and kinds)  widgets.css  home.css
  js/
    lesson-boot.js            course.json + lesson module + trace data + data/anchors.json + glossary.json → sections, quizzes,
                              explain prompts, glossary popovers, prev/next, "mark done"
    home.js                   course map: cards per part, filter box, done ticks, old #deep-link redirect
    core/    dom  state (hash)  store (progress v2)  katex  course  trace (loader, T)  numbers (prose formatter)  sections
             blocks (worked, inTorc, realLine, analogy, chatgpt, refresher, term, sym, loopDiagram)  quiz  popover  chrome
    content/ notation.js (NOTATION, the symbol guide)  refreshers.js (REFRESHERS, the maths refreshers)
    ops/     registry (index.js) + one file per op + tensor.js, texutil.js, elementwise.js
    engine.js  explain.js
    widgets/ graph  stepper  math-window  inputs-popover  graph-lab (the four composed)
    lessons/ <id>.js          lesson modules (and <id>.scenes.js style helpers)
  data/   generated only (tools/trace, plus anchors.json from tools/anchors.mjs)      vendor/katex/
  test/   *.test.mjs, helpers.mjs, v3.mjs (the v3 rules), fixtures/v3-fixture.js (a v3 lesson that exercises every kind and role)
```
- **URLs are relative and prefix-independent.** No `<base>`, nothing root-absolute. Pages find the site root from
  `import.meta.url` (`core/chrome.js`), shells use `../../`. `tools/check_site.mjs` enforces this.
- **Lesson = data + text + widgets.** `js/lessons/<id>.js` exports `{id,title,trace:[files],sections:[…]}`, and a v3 lesson
  also `template: 3`, `loop`, `conceptual`, `sources` ([v3-implementation.md](v3-implementation.md) "Machinery API"). Section
  kinds: `text` (a function `(D, T) => html` over the loaded trace data, rendered in Node by the tests too), `widget`
  (`mount(host, D, ctx)`, browser only, with optional guided `tasks`), `questions`, `quiz`, `explain`, `answer`, `gotcha`, and
  the legacy `tldr`, `predict`, `check`. Rendering is pure (`core/sections.js`, `core/blocks.js`); behaviour is wired after
  rendering by `lesson-boot.js`: `core/quiz.js` (answer, feedback, reveal after the first attempt, the store) and
  `core/popover.js` (glossary definitions on hover, focus and tap). `T('scene.path', role)` puts a number from the trace into
  prose as `<span class="num" data-trace="…" data-role="…" data-sig="…">`, formatted by role (`core/numbers.js`: comma
  thousands separators, exact or 2 significant figures); `T.anchor(name)` and `T.human(path, kind, {of})` are the other two
  forms, and the legacy untagged `T('scene.path')` keeps `fmt`. Every form throws when the path does not exist; a test rejects
  any `.num` without `data-trace` and re-formats every bound one from its attributes. See [authoring.md](authoring.md).
- **Anchors** (`site/anchors.json` → `tools/anchors.mjs` → `site/data/anchors.json`): the values of at most about 15 course-wide
  numbers, copied from their trace paths. `lesson-boot.js` always loads the small output file and sets `D.anchors`, so
  `T.anchor(name)` works in every lesson without the large trace file it comes from. `tools/trace/run.sh` regenerates it after
  the traces, and `--check` fails if it is stale.
- **Progress** (`core/store.js`): `localStorage["torc:v2"] = {lessonId:{visited, done, quiz:{id:{tries, correct}},
  explained:{id:true}, seen:{id:true}}}`. A quiz records every attempt and whether the latest one was right, never a
  self-report. v1 data (`torc:v1`, `{visited, checks, done}`) migrates on first load: v1 checks become `seen`, never `correct`.
  The legacy "I got it" button of a `check` section toggles `seen`. Every access is in try/catch, with an in-memory fallback
  when storage is blocked. "Mark done" is manual. No accounts, no analytics.
- **View state** lives in the hash (`core/state.js`): the Backprop lab uses `#<scene>/<step>`; older links `#mlp/9` on the home
  page are forwarded to `lessons/backprop-lab/#mlp/9` using `legacy_hashes` from `course.json`.
- **Draft lessons** (`status:"draft"`) have a page and module like any other, are reachable by URL and are never listed on the
  home page or in prev/next of other lessons; there are no "coming soon" placeholders.
- **No framework, no build step**; KaTeX is vendored in `site/vendor/katex`.

## Relationship to the library
`main` (TorC) and `web` are separate projects. `web` holds no library code. It depends on TorC through a *pin*:
bump `tools/trace/TORC_REF`, run `tools/trace/run.sh`, review the JSON diff and tests, commit. Do **not** merge `main` into `web`.
Library bugs found while writing lessons are reported with a minimal reproduction and fixed on `main` (see `CLAUDE.md`).

## Testing and CI
- `node --test site/test/` — engine vs. every real run, finite differences (including `transpose` and `mse` on random tensors),
  LaTeX validity, registry completeness, store v2 (migration, blocked storage, sanitize), the prose formatter and `T()` roles,
  course helpers, every lesson rendered in Node (the v3 rules of `site/test/v3.mjs` for `template: 3` lessons, the old budget
  for the others), the v3 fixture and a broken copy for every v3 rule (`v3.test.mjs`), anchors equal to the traces
  (`anchors.test.mjs`), `tools/check_site.mjs` on the real site and on deliberately broken copies. (Node >= 20. On CI the files are passed as
  `site/test/*.test.mjs`; on Node 22 the bare directory form works through `site/test/index.js`.)
- `node tools/check_site.mjs` — course.json valid; every published lesson has its shell (equal to the template), module, trace
  files and page title; no root-absolute URLs; every relative asset reference exists. `--write-shells` regenerates the shells.
- `tools/trace/run.sh --check` — committed JSON equals a fresh run against the pinned TorC, and `site/data/anchors.json` equals the
  traces (`node tools/anchors.mjs --check`).
- `.github/workflows/verify.yml` runs all three on every push/PR touching `site/` or `tools/`; `pages.yml` deploys `site/` on push
  to `web` after the site check and the Node tests.
